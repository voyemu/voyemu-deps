# CI

Twelve GitHub Actions workflows live in `.github/workflows/`: `ci` checks the sources on every change, `release` builds and publishes a release of Voyemu, `kernels` builds and publishes the development kernels, `qnx-host` the QNX engines, `e2fs-helpers` the e2fsprogs image helpers of preparation, `qnx-guest` the QNX guest binaries, `android-native` the native Android components, `android-java` the guest Java code of the profiles, `java-helper` the Java helper of preparation, `java-runtime` the Java runtimes of preparation, `uncrustify` builds and publishes the Uncrustify executables, and `caches` keeps their tool caches alive. They install every tool from its pin and verify its SHA-256, and every action is pinned to a commit. No workflow builds a machine or uses OEM inputs.

## The ci workflow

`ci` runs for pull requests, pushes to `main` and manual dispatch, with read-only repository access; the `release` workflow calls it as well. A newer run on the same branch cancels the older one.

| Job | Runner | What it does |
| --- | --- | --- |
| `source-fixtures` | Ubuntu 24.04, macOS 15, Windows Server 2022 | Installs pinned public fixture prerequisites, builds `native_component_test` and runs the behavior suites labeled `source-fixture` with `oem` excluded; missing suites and skips fail the job |
| `lint` | Ubuntu 24.04 | Configures a Linux tree with Zig and runs `lint` with the pinned formatters, Checkstyle, clang-tidy, Error Prone, Java libraries, D8 and apksigner |
| `linux` | Ubuntu 24.04 | Builds a Linux tree with Zig, runs `voyemu --help` and runs CTest without the `oem` and `deps` labels |
| `tidy-check-windows` | Ubuntu 24.04 | Configures a Windows cross tree with Zig and runs `tidy-check` |
| `macos-native` | macOS 15 | Builds with the Command Line Tools SDK and graphics on, as the release does, runs `voyemu --help`, verifies the code signature and runs CTest without the `oem` and `deps` labels |
| `windows-cross` | Ubuntu 24.04 | Cross-builds Windows executables, checks that no PDB was produced and runs selected PE behavior suites under pinned Wine |
| `windows-native` | Windows Server 2022 | Builds natively, runs `voyemu.exe --help` and runs CTest without the `oem` and `deps` labels |

The jobs repeat the commands of [checks](checks.md), [build](build.md) and [tests](tests.md), so a local run reproduces a CI failure. After the build, `linux`, `macos-native` and `windows-cross` print the size of the launcher and of its sections (`size -A`, `size -m`, `objdump -h`) and `windows-native` its size, so size changes can be compared between commits. Native build jobs run the host-only layer with `--label-exclude 'oem|deps'`. The `source-fixtures` matrix adds the selected dependency behavior suites with pinned public tools and rejects missing suites or skips; these two layers do not establish OEM acceptance. Strict OEM runners need imported originals and fail when inputs are absent. See [test labels](tests.md#registration-and-labels).

### Cross-built Windows tests under Wine

The cross-build job installs Ubuntu 24.04's Wine `9.0~repack-4build3` from three packages (`wine`, `wine64` and `libwine`) pinned by URL and SHA-256 under `optionalTools.linuxBuild.wine` in `src/app/toolchain.json`; Wine uses the runner's system dependencies from its signed APT repositories. This LTS version keeps the cross-build check tied to its Ubuntu runner. `src/dev/ci/wine-tests.cmake` runs the launcher help/version, selected portable PE behavior checks and the `state_replace` regression with unchanged file-incarnation guards. Missing executables, nonzero exits, skipped checks and timeouts fail the job. No check changes Windows ownership or file-incarnation rules for Wine.

The job creates a private Wine prefix and copies only the required executables into its `C:` drive. Its working and temporary directories are ordinary files on `C:`, because Wine's mapped `Z:` root exposes reparse points. The `windows-native` job runs the full host CTest layer, including Windows reparse-point, listener-owner PID and creator DACL contracts. These contracts remain mandatory and are not weakened for Wine capabilities. Xvfb supplies a display, and cleanup stops only that prefix's Wine server.

## Tool caches

Each job installs its tools through the `.github/actions/toolchains` action with one set of `src/dev/ci/toolchains.sh`: Zig, CMake, Ninja, the JDK, the formatters, clang-tidy, Checkstyle, Error Prone, the Java libraries, D8, apksigner and `android.jar` as the job needs, plus the source archives that the CMake configuration would otherwise download. The action caches `.local/toolchains` under a key made of the set name, the runner OS and the hash of every pin file and of the install code, so a changed pin installs and caches a fresh copy and no run downloads an unchanged pin again. Kernel sets also cache the kernel source, the NDK host toolchain, the kernel and ramdisk of the pinned API 30 emulator image and, in a second cache, the host tools and clang that the build stage installs. Builds use no compiler cache.

GitHub removes a cache entry that was not restored for 7 days and keeps at most 10 GB per repository by default, evicting the least recently used entries. The `caches` workflow runs on Mondays and Thursdays and by manual dispatch on the default branch: for every set it runs the same action, which restores the entry and so refreshes it, or installs a missing set from its pins without a build. A missing cache of kernel host tools is rebuilt only by the next `kernels` run. In a public repository GitHub disables scheduled workflows after 60 days without repository activity; re-enable `caches` in the Actions tab then.

## Publishing dependency assets

The nine workflows below publish GitHub Releases in `voyemu/voyemu-deps`. With the new URL and SHA-256 pins committed in `voyemu/voyemu`, push the matching tag to `voyemu/voyemu-deps` using the full commit SHA of the public product source. Push one tag at a time.

```sh
git push git@github.com:voyemu/voyemu-deps.git "$source_commit:refs/tags/$tag"
```

The tag supplies the exact source, pins and workflow to the build. The release job runs in `voyemu/voyemu-deps` with its repository token. Manual runs from `voyemu/voyemu` build and check assets without publishing them.

## The kernels workflow

Development kernels are built in CI and published as GitHub release assets; developers and users on every host download the same image. A profile pins the asset `https://github.com/voyemu/voyemu-deps/releases/download/kernel-<name>-<sha8>/Image` under `android.development_kernel` by URL and SHA-256, `fetch` downloads and verifies it, and `build` uses it. No step of `deps`, `fetch` or `build` compiles a kernel.

`kernels` builds one development kernel recipe, `qinggan-09` or `qinggan-11`, on Ubuntu 24.04. It runs for a tag `kernel-<name>-<sha8>` or by manual dispatch with the recipe name. The job installs the pinned JDK, Zig and NDK through the toolchains action, builds the kernel through `src/prepare/kernel/kernel-tool.sh` and checks the profile pins and release URLs before installing kernel tools, then compares the SHA-256 of the built image with the shared pin. Every profile with the `platform` of the recipe, `qinggan09` or `qinggan11`, that pins a development kernel must pin the same image: Free 6.0.3 the `qinggan-09` image, Free 6.11.1 and Free 7.3.1 the `qinggan-11` image. A tag run then creates the GitHub release with the image, its build record and its descriptor as assets.

`kernel-tool.sh` is the recipe the workflow runs and also the way to reproduce an image outside CI: its `prepare`, `build` and `publish` stages run from pinned sources and tools and yield the same SHA-256 as the pin. The inputs and commands of each recipe are in the `README.md` next to its `component.json`.

To update a kernel, change its recipe, reproduce the image with `kernel-tool.sh`, put its SHA-256 and release URL into every profile that uses the recipe and push the matching tag to `voyemu/voyemu-deps`. The workflow rebuilds the image and publishes it only if it matches the pin. See [components and recipes](../how/components.md) for how profiles consume the kernel.

## The qnx-host workflow

The QNX engine, QEMU 11.1.2 with the patches of `src/app/qnx-host.json`, is built in CI as well, so a host needs neither Python nor a compiler for it. Each recipe section of `qnx-host.json` has a pin under `prebuilt`: `macos_arm64` for the engine of macOS on Apple Silicon, `linux_x64` for Linux x64 and `windows_file_backend` for Windows x64. A pin names the asset `https://github.com/voyemu/voyemu-deps/releases/download/qnx-host-<host>-<sha8>/qnx-host-<host>.zip` by URL and SHA-256, where `<host>` is `macos-arm64`, `linux-x64` or `windows-x64`. `deps` downloads and verifies it; on macOS and Linux the installation record `qnx-host.json` in the archive must name the same recipe, on Windows the files must match `verified_runtime`. While a pin is `null`, its release is pending: `deps` on macOS and Linux builds the engine from the recipe; on Windows, where users never run the recipe, `deps` reports the engine unavailable with `QNX_HOST_ASSET_MISSING` unless an engine is cached, and `build`, `start` and `restart` without `--cluster=on` leave the cluster off.

`qnx-host` runs on demand. Set `reproducible=true` for the first build on a host and after changes to QEMU, its patches, the toolchain or packaging. An unpinned recipe requires this mode. The workflow builds in two project roots of different path and depth and compares the archives byte for byte. A successful run uploads a checked archive and records the source commit, host and SHA-256. Each host uses its pinned recipe and runner, macOS 15, Ubuntu 24.04 or Windows Server 2022. The archive is a stored ZIP in name order with a fixed time and no owner. It contains the installation record on macOS and Linux and the runtime files on Windows.

Run `gh workflow run qnx-host.yml --repo voyemu/voyemu --ref main -f host=windows-x64 -f reproducible=true` to verify Windows. Enter the URL and SHA-256 from the run summary into `prebuilt`. For Windows, also pin the SHA-256 and size of `qemu-system-aarch64.exe` in `verified_runtime` and set its `qnx_file_backend.engine_sha256`. Push the matching resource tag to `voyemu/voyemu-deps` from that source snapshot with only the publication pins changed. Dispatch with `gh workflow run qnx-host.yml --repo voyemu/voyemu-deps --ref TAG -f verified_run=RUN_ID`. By default the workflow looks up the run in `voyemu/voyemu-deps`. For a producer run in `voyemu/voyemu`, set the dependency repository secret `QNX_ARTIFACT_READ_TOKEN` to a token with Actions read access to the product repository. To avoid a cross-repository token, dispatch the producer from a branch in `voyemu/voyemu-deps` containing the same recipe snapshot and full workflow. If the artifact expired or the run ID is omitted, the tag workflow builds once. In both cases it verifies the pinned SHA-256 before publishing the ZIP, build record and corresponding-source companion. A recipe change requires a new pin.

## The e2fs-helpers workflow

Preparation edits ext4 images of Free 6.0.3 machines and API 30 machines with two own helpers on libext2fs: `a9-offline-labels` and `api30-root-layout`. Both are built in CI from the pinned e2fsprogs release tarball under `e2fsprogs` in `src/app/toolchain.json` and the sources in `src/app/prepare/`. `e2fsprogs.helpers` pins each executable per host, `https://github.com/voyemu/voyemu-deps/releases/download/e2fs-helpers-<sha8>/<helper>-<host>` for `linux-x64`, `darwin-arm64` and `win32-x64`, where `<sha8>` starts the SHA-256 of `SHA256SUMS`, the list of the six executables. Preparation downloads the helper of its host into `.local/toolchains/e2fs-helpers/<sha256>/`, on Windows with the `.exe` suffix, and checks it against the pin on every use. While the release of the asset is not published, so its server answers HTTP 404, preparation builds the helper with the recipe below and the pinned Zig and CMake of the host and checks it against the same pin; the log names the path taken. A download that fails for another reason, such as a missing network, stops with its error instead of building from the recipe; this holds for every recipe below. The recipe runs the e2fsprogs `configure` and `make`, so a Windows host, which has neither, needs the published asset.

`e2fs-helpers` runs on Ubuntu 24.04 for a tag `e2fs-helpers-<sha8>` or by manual dispatch. `src/dev/ci/e2fs-helpers-select.sh` derives the tag from the pins and checks the URLs and the tag. With the Zig and CMake of the `linux` set, `src/app/prepare/e2fsprogs_build.cmake` builds libext2fs and both helpers for each host: the Linux ones with the [glibc baseline](build.md#configure-and-build) of the launcher, which they take from `src/dev/toolchains/zig-linux-x64.cmake`, the macOS ones against the macOS headers and libraries bundled with Zig and the Windows ones against MinGW with the Windows I/O manager of libext2fs, so they do not depend on the SDK of a build host. Each executable is built twice, each time in a new directory that the file prefix map removes from the output; both copies must match each other byte for byte and match the pin. The job then runs the shell tests of both helpers with the Linux executables and the e2fsprogs tools of the runner. A tag run creates the release with the executables, `SHA256SUMS` and the e2fsprogs `NOTICE` as assets.

`cmake -DVOYEMU_E2FS_TARGET=<host> -DVOYEMU_E2FS_OUTPUT=<directory> -P src/app/prepare/e2fsprogs_build.cmake` is the recipe the workflow runs and also the way to reproduce the helpers outside CI on any host with a POSIX shell and `make`. A change of a helper source or of the e2fsprogs pin changes the executables: rebuild them with this command, put their SHA-256 and the URLs of the new tag into `e2fsprogs.helpers` and push the tag to `voyemu/voyemu-deps`.

## The qnx-guest workflow

The QNX guests of the Free 6.0.3, 6.11.1 and 7.3.1 and Passion profiles run own binaries: the front and observer libraries, the OpenWF display library, the Passion RAM carrier and the boot blobs of the QNX images. CI builds them from `src/guest/qnx/` and the Khronos headers pinned in its `component.json`; no OEM input and no NDK take part. Each library links with its imports undefined and needs only `libc.so.4` and, for the front library, `libscreen.so.1`, which the QNX runtime linker of the guest resolves. The front library of Free 6.0.3 reserves the section `.voyemu_oem` of fixed size for the OEM startup script and the OEM `sysmgrtool`, which `build` writes into it as data.

`qnxGuestModules` in `src/app/toolchain.json` pins each binary per hardware adapter, `https://github.com/voyemu/voyemu-deps/releases/download/qnx-guest-<sha8>/<adapter>-<file>` for `sa8155-qinggan09`, `sa8155-qinggan11-731`, `sa8155-qinggan11-611` and `sa8155-passion-21480`, where `<sha8>` starts the SHA-256 of `SHA256SUMS`, the list of all binaries, and records the initial native state that the front library of Free 6.11.1 and 7.3.1 is built with. `build` downloads the set of its hardware adapter into `.local/toolchains/qnx-guest/<digest>/` and checks it against the pins on every use; it then checks that the OEM libraries of the profile export every import. While the assets are not published, so their server answers HTTP 404, `build` runs the recipe with the pinned Zig of the developer tools and checks the result against the same pins; without that Zig it stops with `QNX_GUEST_ASSET_MISSING`.

`qnx-guest` runs on Ubuntu 24.04 for a tag `qnx-guest-<sha8>` or by manual dispatch. `src/dev/ci/qnx-guest-select.sh` derives the tag from the pins and checks the URLs and the tag. With the tools of the `linux` set the job builds the test executable `qnx_guest_build_test`, whose `--recipe ROOT OUTPUT` mode runs the recipe `build_qnx_guest_recipe` for the four hardware adapters with the clang and ld.lld of the pinned Zig. The binaries are built twice; both copies must match each other byte for byte and match the pins. A tag run creates the release with the binaries and `SHA256SUMS` as assets. The `qnx_guest_build` test of the `ci` workflow runs the recipe of the `sa8155-qinggan09` set on every host and compares it with the pins.

A change of a guest source changes the binaries: run `qnx_guest_build_test --recipe "$PWD" "$PWD/.local/build/qnx-guest"`, put the SHA-256 of the files and the URLs of the new tag into `qnxGuestModules` and push the tag to `voyemu/voyemu-deps`.

## The android-native workflow

The native components of the profiles, the CAN model and simulator, the early input helper, the runtime and input method libraries and the multi-display libraries, are built in CI from their component sources and the AOSP sources pinned in their `component.json`, with the pinned NDK and no OEM input. A library with `guestLibs` links against stubs that carry only the sonames of those libraries of the Android image, so its imports stay undefined for the Android linker; `build` checks that the libraries of the image, with `libc.so`, `libm.so`, `libdl.so` and `libc++.so`, export every import.

`androidNativeComponents` in `src/app/toolchain.json` pins each component by `<profile>/<component>`, `https://github.com/voyemu/voyemu-deps/releases/download/android-native-<sha8>/<profile>-<component>-<output>`, where `<sha8>` starts the SHA-256 of `SHA256SUMS`, the list of all components. `build` downloads the components of the profile into `.local/toolchains/android-native/<sha256>/` and checks them against the pins on every use. Bionic headers and libraries come only with the NDK, so no recipe runs without it: while an asset is not published, so its server answers HTTP 404, `build` runs the recipe with the pinned NDK under `.local/toolchains/native-sdk/ndk/` when a developer installed it and checks the result against the same pin, and otherwise stops with `ANDROID_NATIVE_ASSET_MISSING`.

`android-native` runs on Ubuntu 24.04 for a tag `android-native-<sha8>` or by manual dispatch. `src/dev/ci/android-native-select.sh` derives the tag from the pins and checks the URLs and the tag. The toolchains action installs the `linux` set with the source-fixture inputs, which include the NDK; the job builds the test executable `native_component_test`, whose `--recipe ROOT OUTPUT --online` mode runs `build_native_component_recipe` for every native component of every profile. The components are built twice; both copies must match each other byte for byte and match the pins. A tag run creates the release with the components and `SHA256SUMS` as assets.

A change of a native component changes its asset: run `native_component_test --recipe "$PWD" "$PWD/.local/build/android-native" --online`, put the SHA-256 of the files and the URLs of the new tag into `androidNativeComponents` and push the tag to `voyemu/voyemu-deps`.

## The android-java workflow

The profiles' own guest Java code, the Java sources of their components and of their patch steps, is compiled in CI as well, with javac of the pinned JDK at `--release 8` and D8 of the pinned build tools against the pinned `android.jar`, and no OEM input. A unit is a source directory with its `compile-only/` declarations, optional sources that aapt2 generates from the component resources and the minimum API; its key is the SHA-256 of the relative path and SHA-256 of every input file, the minimum API and the platform JAR. `android-java.zip` holds `<key>/classes*.dex` of every unit of every profile, `observer/classes.dex`, the UI observer of `src/guest/android/api` without its host tests, and `index.json`, which names the profile and source of each key and the SHA-256 of each observer source. `androidJava` in `src/app/toolchain.json` pins it, `https://github.com/voyemu/voyemu-deps/releases/download/android-java-<sha8>/android-java.zip`, where `<sha8>` starts the SHA-256 of `SHA256SUMS`. `build` downloads it into `.local/toolchains/android-java/<sha256>/`, and the Java helper reads the DEX of each unit by its key and stops with `ANDROID_JAVA_MISSING` when the asset lacks a unit, as after a change of a guest source. With `--jdk`, the helper can compile changed units from their sources; the default Java runtime has no javac and needs the pinned asset. A Java runtime without javac takes the observer from the asset as well; `build` stops with `ANDROID_JAVA_MISSING` when the observer of the asset was built from other sources. Sources that use OEM classes, such as the components with an OEM donor DEX, the synthetic phone of Free 6.11.1 and 7.3.1 and the USB player and MCU property helpers, compile against `compile-only/` declarations of exactly the OEM members they use: names, signatures and constant values without code.

`android-java` runs on Ubuntu 24.04 for a tag `android-java-<sha8>` or by manual dispatch. `src/dev/ci/android-java-select.sh` derives the tag from the pin and checks the URL and the tag. The toolchains action installs the `linux` set with the source-fixture inputs, which include the Maven libraries, the build tools and `android.jar`; the job compiles the helper sources and runs `GuestJavaRecipe`, which materializes the component sources of every profile as `build` does, with their pinned external sources, links the resources of the APK components with aapt2 and compiles every unit. The archive is built twice; both copies must match each other byte for byte and match the pin. A tag run creates the release with `android-java.zip` and `SHA256SUMS` as assets.

A change of a guest source changes the archive: compile the helper sources, run `java -cp CLASSES:LIBRARIES com.voyemu.prepare.GuestJavaRecipe "$PWD" "$PWD/.local/toolchains/java-sdk" "$PWD/.local/build/android-java"` with the pinned JDK, put the SHA-256 of `android-java.zip` and the URL of the new tag into `androidJava` and push the tag to `voyemu/voyemu-deps`.

## The java-helper workflow

The Java helper of preparation is built in CI too: `src/prepare/JavaHelperBuild.java` compiles `src/prepare/java` with javac of the pinned JDK against the Maven libraries pinned in `src/prepare/libraries.json` and the JARs of the pinned build tools. `java-helper.zip` holds `voyemu-java-helper.jar`, its `build-receipt.json` with the JAR and external dependency checksums, and the Maven libraries under `lib/`; `d8.jar` and `apksigner.jar` are not in it, preparation takes them from the build tools archive. `javaHelper` in `src/app/toolchain.json` pins it, `https://github.com/voyemu/voyemu-deps/releases/download/java-helper-<sha8>/java-helper.zip`, where `<sha8>` starts the SHA-256 of `SHA256SUMS`.

Without `--jdk`, preparation installs this asset even in a source checkout. It adds the two SDK JARs and publishes the helper into `.local/toolchains/java-helper/<fingerprint>/`; this cache key binds the asset pin and the external library pins. A missing or unreachable asset produces `JAVA_HELPER_ASSET_MISSING`, without compiling a replacement. In a source checkout, `--jdk PATH` selects the developer recipe instead; its cache key also includes the actual helper sources and resource inputs. Both routes verify the JAR, build receipt and complete set of external dependencies, and bind the selected key to the ownership receipt and cache directory. An incomplete cache without ownership is retained and rejected. Source hashes used for the developer cache and in-operation checks are not persisted as compatibility requirements for a prepared machine.

`java-helper` runs on Ubuntu 24.04 for a tag `java-helper-<sha8>` or by manual dispatch. `src/dev/ci/java-helper-select.sh` derives the tag from the pin and checks the URL and the tag. The toolchains action installs the `linux` set with the source-fixture inputs; the job builds the archive twice with sorted entries and the earliest ZIP time; both copies must match each other byte for byte and match the pin. A tag run creates the release with `java-helper.zip` and `SHA256SUMS` as assets.

A change of a helper source or of a library pin changes the archive: run `javac --release 25 -d .local/build/java-helper/recipe src/prepare/java/com/voyemu/prepare/Json.java src/prepare/JavaHelperBuild.java`, then `java -cp .local/build/java-helper/recipe com.voyemu.prepare.JavaHelperBuild asset "$PWD" "$PWD/.local/toolchains/java/libraries" "$PWD/.local/build/java-helper/asset"` with the pinned JDK, put the SHA-256 of `java-helper.zip` and the URL of the new tag into `javaHelper` and push the tag to `voyemu/voyemu-deps`.

## The java-runtime workflow

The Java runtime of preparation is a minimal image that jlink links from the jmods of the pinned Temurin JDK 25 release, one per host. `javaRuntime` in `src/app/toolchain.json` pins the JDK version, the module list, the jmods archive of each host by URL and SHA-256 and each runtime under `javaRuntime.assets`: `https://github.com/voyemu/voyemu-deps/releases/download/java-runtime-<sha8>/java-runtime-<host>.zip` for `darwin-arm64`, `linux-x64` and `win32-x64`, where `<sha8>` starts the SHA-256 of `SHA256SUMS`, the list of the three archives. `deps` downloads the runtime of its host into `.local/toolchains/java-runtime/<sha256>/`, and the Java helper runs on it unless `--jdk` names a JDK. While the asset is not published, so its server answers HTTP 404, `deps` links the runtimes with the recipe below on the pinned JDK of the developer tools and checks the archive of the host against the same pin; without that JDK it reports the runtime unavailable with `JAVA_RUNTIME_ASSET_MISSING`.

`java-runtime` runs on Ubuntu 24.04 for a tag `java-runtime-<sha8>` or by manual dispatch. `src/dev/ci/java-runtime-select.sh` derives the tag from the pins and checks the URLs and the tag. With the JDK of the `linux` set, `src/prepare/JavaRuntimeBuild.java` downloads the three jmods archives, links each runtime with the jlink of that JDK, which must be the pinned version, and writes a ZIP with sorted entries, the earliest ZIP time and Unix modes. jlink links the jmods of a foreign host as well, so one Linux runner builds all three. The runtime keeps only the pinned modules and drops the Java debug attributes, header files and manual pages; native symbols stay, because their stripping needs the objcopy of the host, which cannot read Mach-O and PE files. The recipe disables jlink's optional ahead-of-time generation of method-handle classes because its plugin can run before or after Java debug stripping, changing the archive bytes. A class data sharing archive would have to be generated by the runtime of each host itself, so the runtime has none. Each archive is built twice; both copies must match each other byte for byte and match the pins. A tag run creates the release with the archives and `SHA256SUMS` as assets; the license texts of the JDK are under `java-runtime/legal/`.

A change to the build recipe, modules or JDK can change the archives: run `javac -d .local/build/java-runtime/recipe src/prepare/java/com/voyemu/prepare/Json.java src/prepare/JavaRuntimeBuild.java`, then `java -cp .local/build/java-runtime/recipe com.voyemu.prepare.JavaRuntimeBuild "$PWD" "$PWD/.local/toolchains/downloads/java-runtime" "$PWD/.local/build/java-runtime/asset"` with the pinned JDK, put the SHA-256 of the archives and the URLs of the new tag into `javaRuntime.assets` and push the tag to `voyemu/voyemu-deps`. `java -cp .local/build/java-runtime/recipe com.voyemu.prepare.JavaRuntimeBuild modules "$PWD" HELPER_JAR` prints the modules that jdeps finds in a built helper and its libraries and fails when one is not pinned.

## The uncrustify workflow

The formatter Uncrustify is built in CI as well, so no host needs Python or a compiler for it. `src/app/toolchain.json` pins the upstream release tarball under `optionalTools.uncrustify` as the recipe input and the executable of each host under `optionalTools.uncrustify.binaries`: `https://github.com/voyemu/voyemu-deps/releases/download/uncrustify-<version>-<sha8>/uncrustify-<version>-<host>` for `linux-x64`, `darwin-arm64` and `win32-x64`, the last with `.exe`. `<sha8>` starts the SHA-256 of `SHA256SUMS`, the list of the three executables, so the tag names the whole set. `cmake -P src/dev/format/uncrustify.cmake` downloads the executable of the host and checks it; see [checks](checks.md#formatting-and-checkstyle).

`uncrustify` runs on Ubuntu 24.04 for a tag `uncrustify-<version>-<sha8>` or by manual dispatch. `src/dev/ci/uncrustify-select.sh` first derives the tag from the pins and checks that every URL names its asset in that release of `voyemu/voyemu-deps` and that a tag run uses that tag. The job installs Zig, CMake, Ninja and the tarball through the toolchains action and builds all three executables with Zig on Linux: the Linux one with `src/dev/toolchains/zig-linux-x64.cmake`, the Windows one with `zig-windows-x64.cmake` and the macOS one against the macOS headers and libraries bundled with Zig, so it does not depend on the SDK of a build host. Upstream generates its option tables with the Python 3 of the runner. Each executable is built twice, each time in a new directory that the file prefix map removes from the output; both copies must match each other byte for byte and match the pin. A tag run then creates the release with the three executables and `SHA256SUMS` as assets.

`cmake -DVOYEMU_UNCRUSTIFY_TARGET=<host> -DVOYEMU_UNCRUSTIFY_OUTPUT=<file> -P src/dev/format/uncrustify.cmake` is the recipe the workflow runs and also the way to reproduce an executable outside CI. To update Uncrustify, change the tarball pin, build the three executables with this command, put their SHA-256 and the URLs of the new tag into `optionalTools.uncrustify.binaries` and push the tag to `voyemu/voyemu-deps`. The `lint` set installs the released executable and, while that release does not exist yet, builds it from source; both paths check the same pin.

## The release workflow

`release` runs for a stable tag pushed to GitHub or for a manual run on a prerelease tag. The tag names the `VOYEMU_VERSION` of `src/app/CMakeLists.txt`, see [release](release.md#version). It first calls `ci`. A Windows-only prerelease runs native Windows checks, Wine and the Windows cross-build checks, both Windows and Linux source fixtures, Linux tests and lint. For an all-host release, three jobs build the launcher with `BUILD_TESTING=OFF` and the toolchain sets of the `ci` jobs: macOS arm64 on macOS 15 with the graphics worker, Linux x64 on Ubuntu 24.04 and Windows x64 cross-built on Ubuntu 24.04. The macOS and Linux jobs check that the launcher reports the version of the tag, macOS also verifies the code signature and the Windows job checks that no PDB was produced; each job installs the `Runtime` component and uploads the launcher and `notices/`. The `package` job runs `src/dev/release/archive.sh` for the selected hosts, writes `SHA256SUMS`, fills in the Homebrew formula with `src/dev/release/homebrew.sh` for a stable version and takes the release notes from the section of the version in `CHANGELOG.md` with `src/dev/release/notes.sh`. The `windows-archive` job runs on native Windows, checks the ZIP's SHA-256 against `SHA256SUMS`, extracts the ZIP and verifies the launcher's version. The `release` job creates the GitHub release with the archives and `SHA256SUMS`, a prerelease for a version with a suffix, and is the only job with write access. For a stable version the `homebrew` job commits the formula as `Formula/voyemu.rb` to `voyemu/homebrew-tap` with the `HOMEBREW_TAP_TOKEN` secret, a token with write access to that repository; without the secret it leaves the tap unchanged and says so in the run.
