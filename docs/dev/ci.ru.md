# CI

В `.github/workflows/` двенадцать рабочих процессов GitHub Actions (workflow): `ci` проверяет исходники при каждом изменении, `release` собирает и публикует релиз Voyemu, `kernels` собирает и публикует ядра разработки, `qnx-host` — движки QNX, `e2fs-helpers` — помощники e2fsprogs для подготовки, `qnx-guest` — гостевые двоичные файлы QNX, `android-native` — нативные компоненты Android, `android-java` — гостевой код Java профилей, `java-helper` — помощник Java подготовки, `java-runtime` — среды Java для подготовки, `uncrustify` собирает и публикует исполняемые файлы Uncrustify, а `caches` поддерживает их кеши инструментов. Они устанавливают каждый инструмент по его пину и сверяют SHA-256, а каждое действие закреплено коммитом. Ни один рабочий процесс не подготавливает машину и не использует оригиналы.

## Рабочий процесс ci

`ci` запускается для запросов на слияние, отправок в `main` и вручную, с доступом к репозиторию только на чтение; его также вызывает рабочий процесс `release`. Новый запуск в той же ветке отменяет старый.

| Задание | Среда | Что делает |
| --- | --- | --- |
| `source-fixtures` | Ubuntu 24.04, macOS 15, Windows Server 2022 | Устанавливает закреплённые общедоступные инструменты для тестовых данных, собирает `native_component_test` и запускает проверки поведения с меткой `source-fixture`, исключая `oem`; если набора нет или тест пропущен, задание завершается ошибкой |
| `lint` | Ubuntu 24.04 | Настраивает дерево Linux с Zig и запускает `lint` с закреплёнными средствами форматирования, Checkstyle, clang-tidy, Error Prone, библиотеками Java, D8 и apksigner |
| `linux` | Ubuntu 24.04 | Собирает дерево Linux с Zig, запускает `voyemu --help` и CTest без меток `oem` и `deps` |
| `tidy-check-windows` | Ubuntu 24.04 | Настраивает дерево кросс-сборки для Windows с Zig и запускает `tidy-check` |
| `macos-native` | macOS 15 | Собирает с SDK из Command Line Tools и графикой, как релиз, запускает `voyemu --help`, проверяет подпись кода и запускает CTest без меток `oem` и `deps` |
| `windows-cross` | Ubuntu 24.04 | Собирает Windows кросс-сборкой, проверяет отсутствие PDB и запускает выбранные поведенческие PE-тесты под закреплённым Wine |
| `windows-native` | Windows Server 2022 | Собирает на Windows, запускает `voyemu.exe --help` и CTest без меток `oem` и `deps` |

Задания повторяют команды [проверок](checks.ru.md), [сборки](build.ru.md) и [тестов](tests.ru.md), поэтому локальный запуск воспроизводит сбой CI. После сборки `linux`, `macos-native` и `windows-cross` печатают размер лаунчера и его секций (`size -A`, `size -m`, `objdump -h`), а `windows-native` — размер файла, чтобы сравнивать размер между коммитами. Задания нативной сборки запускают слой хоста с `--label-exclude 'oem|deps'`. Матрица `source-fixtures` добавляет выбранные проверки поведения с общедоступными закреплёнными инструментами и считает ошибкой отсутствие набора или пропуск; эти два слоя не заменяют приёмку с оригиналами. Строгие тесты с оригиналами требуют их импорта и без них завершаются ошибкой. См. [метки тестов](tests.ru.md#регистрация-и-метки).

### Windows-тесты кросс-сборки под Wine

Задание кросс-сборки устанавливает Wine `9.0~repack-4build3` из Ubuntu 24.04: URL и SHA-256 трёх пакетов `wine`, `wine64` и `libwine` закреплены в `optionalTools.linuxBuild.wine` файла `src/app/toolchain.json`, а системные зависимости берутся из подписанных репозиториев APT исполнителя. Эта версия LTS привязывает проверку к выбранной Ubuntu. `src/dev/ci/wine-tests.cmake` запускает справку и версию лаунчера, выбранные переносимые поведенческие проверки PE и регрессию `state_replace` с прежними проверками идентичности файла. Отсутствующий исполняемый файл, ненулевой код завершения, пропуск или тайм-аут завершают задание ошибкой. Правила Windows для владельца файла и его идентичности под Wine не ослабляются.

Задание создаёт отдельное окружение Wine и копирует только нужные исполняемые файлы на его диск `C:`. Рабочий каталог и временные файлы находятся на `C:`: отображение корня хоста на `Z:` создаёт точки повторного анализа. Задание `windows-native` запускает полный слой CTest хоста, включая проверки точек повторного анализа Windows, PID владельца слушающего сокета и DACL создателя. Эти проверки обязательны и не ослабляются из-за возможностей Wine. Xvfb предоставляет дисплей, а очистка останавливает сервер Wine только этого окружения.

## Кеши инструментов

Каждое задание устанавливает свои инструменты через действие `.github/actions/toolchains` с одним набором из `src/dev/ci/toolchains.sh`: Zig, CMake, Ninja, JDK, средства форматирования, clang-tidy, Checkstyle, Error Prone, библиотеки Java, D8, apksigner и `android.jar` по потребностям задания, а также архивы исходников, которые иначе скачала бы настройка CMake. Действие кеширует `.local/toolchains` под ключом из имени набора, ОС исполнителя CI и хеша всех файлов пинов и кода установки, поэтому после изменения пина действие устанавливает и кеширует свежую копию, а неизменный пин ни один запуск не скачивает повторно. Наборы ядер кешируют также исходники ядра, набор инструментов NDK для хоста, ядро и ramdisk закреплённого образа эмулятора API 30 и, во втором кеше, инструменты хоста и clang, которые устанавливает стадия сборки. Кеш компилятора сборки не используют.

GitHub удаляет запись кеша, которую не восстанавливали 7 дней, и по умолчанию хранит не больше 10 ГБ на репозиторий, вытесняя давно не использованные записи. Рабочий процесс `caches` запускается по понедельникам и четвергам и вручную на основной ветке: для каждого набора он выполняет то же действие: оно восстанавливает запись и тем самым обновляет её, а отсутствующий набор устанавливает по пинам без сборки. Отсутствующий кеш инструментов хоста для ядра пересоберёт только следующий запуск `kernels`. В публичном репозитории GitHub отключает запуски по расписанию после 60 дней без активности в репозитории; тогда `caches` нужно снова включить на вкладке Actions.

## Публикация ресурсов

Девять рабочих процессов ниже публикуют релизы в `voyemu/voyemu-deps`. Порядок публикации: зафиксировать новые URL и SHA-256 в `voyemu/voyemu`, затем отправить соответствующий тег в `voyemu/voyemu-deps` с полным SHA публичного коммита Voyemu. Теги отправляются по одному.

```sh
git push git@github.com:voyemu/voyemu-deps.git "$source_commit:refs/tags/$tag"
```

Тег задаёт исходники, пины и рабочий процесс для сборки. Задание публикации выполняется в `voyemu/voyemu-deps` с токеном этого репозитория. Ручные запуски из `voyemu/voyemu` собирают и проверяют ресурсы без публикации.

## Рабочий процесс kernels

Ядра разработки собираются в CI и публикуются как ресурсы релизов GitHub; разработчики и пользователи на любом хосте скачивают один и тот же образ. Профиль закрепляет ресурс `https://github.com/voyemu/voyemu-deps/releases/download/kernel-<name>-<sha8>/Image` в `android.development_kernel` по URL и SHA-256, `fetch` скачивает и сверяет его, а `build` использует. Ни `deps`, ни `fetch`, ни `build` ядро не компилируют.

`kernels` собирает один рецепт ядра разработки, `qinggan-09` или `qinggan-11`, на Ubuntu 24.04. Он запускается для тега `kernel-<name>-<sha8>` или вручную с именем рецепта. Задание устанавливает закреплённые JDK, Zig и NDK через действие `toolchains`, собирает ядро через `src/prepare/kernel/kernel-tool.sh` и сравнивает SHA-256 собранного образа с общим пином. До установки инструментов рабочий процесс проверяет пины профилей и URL релизов. Каждый профиль с `platform` рецепта, `qinggan09` или `qinggan11`, закрепляющий ядро разработки, должен закреплять один и тот же образ: Free 6.0.3 — образ `qinggan-09`, Free 6.11.1 и Free 7.3.1 — образ `qinggan-11`. Запуск по тегу затем создаёт релиз GitHub, ресурсами которого становятся образ, запись о сборке и дескриптор.

`kernel-tool.sh` — рецепт, который выполняет рабочий процесс, и способ воспроизвести образ вне CI: этапы `prepare`, `build` и `publish` работают с закреплёнными исходниками и инструментами и дают тот же SHA-256, что и пин. Входы и команды каждого рецепта описаны в `README.md` рядом с его `component.json`.

Обновление ядра: изменить его рецепт, воспроизвести образ через `kernel-tool.sh`, внести его SHA-256 и URL релиза во все профили, которые используют рецепт, и отправить соответствующий тег в `voyemu/voyemu-deps`. Рабочий процесс заново собирает образ и публикует его, только если тот совпадает с пином. Как профили используют ядро, описано в [компонентах и рецептах](../how/components.ru.md).

## Рабочий процесс qnx-host

Движок QNX — QEMU 11.1.2 с патчами из `src/app/qnx-host.json` — тоже собирается в CI, и хосту не нужны для него ни Python, ни компилятор. У каждого раздела рецепта в `qnx-host.json` есть пин в `prebuilt`: `macos_arm64` для движка macOS на Apple Silicon, `linux_x64` для Linux x64 и `windows_file_backend` для Windows x64. Пин закрепляет ресурс `https://github.com/voyemu/voyemu-deps/releases/download/qnx-host-<host>-<sha8>/qnx-host-<host>.zip` по URL и SHA-256, где `<host>` — `macos-arm64`, `linux-x64` или `windows-x64`. `deps` скачивает и сверяет его: на macOS и Linux запись об установке `qnx-host.json` в архиве должна называть тот же рецепт, на Windows файлы должны совпасть с `verified_runtime`. Пока пин равен `null`, релиз ещё не опубликован: на macOS и Linux `deps` собирает движок по рецепту; на Windows, где пользователи рецепт не запускают, `deps` сообщает с кодом `QNX_HOST_ASSET_MISSING`, что движок недоступен, если в кеше нет движка, а `build`, `start` и `restart` без `--cluster=on` оставляют приборку выключенной.

`qnx-host` запускается вручную. Параметр `reproducible=true` нужен при первой сборке для хоста и после изменений QEMU, его патчей, набора инструментов или упаковки. Рецепт без пина требует этого режима. Рабочий процесс собирает движок в двух каталогах разной глубины и побайтно сравнивает архивы. После успешной проверки он сохраняет архив и записывает коммит исходников, хост и SHA-256. Сборка использует закреплённый рецепт на исполнителе своего хоста — macOS 15, Ubuntu 24.04 или Windows Server 2022. ZIP без сжатия хранит файлы по порядку имён, с фиксированным временем и без владельца. На macOS и Linux он включает запись об установке, на Windows — файлы среды выполнения.

Проверка Windows: запустить `gh workflow run qnx-host.yml --repo voyemu/voyemu --ref main -f host=windows-x64 -f reproducible=true`. Внести URL и SHA-256 из сводки в `prebuilt`. Для Windows также закрепить SHA-256 и размер `qemu-system-aarch64.exe` в `verified_runtime` и заполнить `qnx_file_backend.engine_sha256`. Отправить соответствующий тег ресурсов в `voyemu/voyemu-deps` из того же снимка исходников, изменив только пины публикации. Запустить `gh workflow run qnx-host.yml --repo voyemu/voyemu-deps --ref TAG -f verified_run=RUN_ID`. По умолчанию рабочий процесс ищет прогон в `voyemu/voyemu-deps`. Для прогона из `voyemu/voyemu` в репозитории ресурсов нужен секрет `QNX_ARTIFACT_READ_TOKEN` с правом чтения Actions в основном репозитории. Без отдельного токена сборка запускается из ветки `voyemu/voyemu-deps` с тем же снимком рецепта и полным рабочим процессом. Если артефакт истёк или номер прогона не указан, рабочий процесс собирает движок один раз. В обоих случаях он сверяет закреплённый SHA-256 и публикует ZIP, запись сборки и архив соответствующих исходников. Изменение рецепта требует нового пина.

## Рабочий процесс e2fs-helpers

Подготовка правит образы ext4 машин Free 6.0.3 и машин API 30 двумя собственными помощниками на libext2fs: `a9-offline-labels` и `api30-root-layout`. Оба собираются в CI из закреплённого архива релиза e2fsprogs (`e2fsprogs` в `src/app/toolchain.json`) и исходников из `src/app/prepare/`. `e2fsprogs.helpers` закрепляет каждый исполняемый файл для каждого хоста: `https://github.com/voyemu/voyemu-deps/releases/download/e2fs-helpers-<sha8>/<helper>-<host>` для `linux-x64`, `darwin-arm64` и `win32-x64`, где `<sha8>` — начало SHA-256 файла `SHA256SUMS` со списком шести исполняемых файлов. Подготовка скачивает помощника своего хоста в `.local/toolchains/e2fs-helpers/<sha256>/`, на Windows с суффиксом `.exe`, и сверяет его с пином при каждом использовании. Пока релиз ресурса не опубликован и сервер отвечает HTTP 404, подготовка собирает помощника по рецепту ниже закреплёнными Zig и CMake хоста и сверяет с тем же пином; лог называет выбранный путь. Загрузка, которая не удалась по другой причине, например без сети, останавливается с ошибкой без сборки по рецепту; это верно для всех рецептов ниже. Рецепт запускает `configure` и `make` из e2fsprogs, поэтому хосту Windows, где их нет, нужен опубликованный ресурс.

`e2fs-helpers` запускается на Ubuntu 24.04 для тега `e2fs-helpers-<sha8>` или вручную. `src/dev/ci/e2fs-helpers-select.sh` выводит тег из пинов и проверяет URL и тег. С Zig и CMake из набора `linux` скрипт `src/app/prepare/e2fsprogs_build.cmake` собирает libext2fs и оба помощника для каждого хоста. Помощники Linux получают [базу glibc](build.ru.md#настройка-и-сборка) лаунчера из `src/dev/toolchains/zig-linux-x64.cmake`, помощники macOS собираются с заголовками и библиотеками macOS из поставки Zig, помощники Windows — с MinGW и модулем ввода-вывода Windows из libext2fs; ни один не зависит от SDK хоста сборки. Каждый исполняемый файл собирается дважды, каждый раз в новом каталоге, который карта префиксов файлов убирает из результата; обе копии должны побайтно совпасть друг с другом и с пином. Затем задание прогоняет тестовые скрипты обоих помощников с исполняемыми файлами Linux и инструментами e2fsprogs исполнителя CI. Запуск по тегу создаёт релиз, ресурсами которого становятся исполняемые файлы, `SHA256SUMS` и `NOTICE` из e2fsprogs.

`cmake -DVOYEMU_E2FS_TARGET=<host> -DVOYEMU_E2FS_OUTPUT=<directory> -P src/app/prepare/e2fsprogs_build.cmake` — рецепт, который выполняет рабочий процесс, и способ воспроизвести помощников вне CI на любом хосте с командной оболочкой POSIX и `make`. Правка исходника помощника или пина e2fsprogs меняет исполняемые файлы: нужно пересобрать их этой командой, внести SHA-256 и URL нового тега в `e2fsprogs.helpers` и отправить тег в `voyemu/voyemu-deps`.

## Рабочий процесс qnx-guest

Гости QNX профилей Free 6.0.3, 6.11.1 и 7.3.1 и Passion запускают собственные двоичные файлы: библиотеки front и observer, библиотеку дисплея OpenWF, носитель RAM Passion и загрузочные блоки образов QNX. CI собирает их из `src/guest/qnx/` и заголовков Khronos, закреплённых в его `component.json`; ни оригиналы, ни NDK не участвуют. Каждая библиотека компонуется с неразрешёнными импортами и требует только `libc.so.4`, а библиотека front ещё и `libscreen.so.1`; их разрешает компоновщик времени выполнения QNX в госте. Библиотека front профиля Free 6.0.3 резервирует секцию `.voyemu_oem` фиксированного размера для штатного скрипта запуска и штатного `sysmgrtool`, которые `build` записывает в неё как данные.

`qnxGuestModules` в `src/app/toolchain.json` закрепляет каждый двоичный файл для каждого аппаратного адаптера, `https://github.com/voyemu/voyemu-deps/releases/download/qnx-guest-<sha8>/<adapter>-<file>` для `sa8155-qinggan09`, `sa8155-qinggan11-731`, `sa8155-qinggan11-611` и `sa8155-passion-21480`, где `<sha8>` — начало SHA-256 файла `SHA256SUMS` со списком всех двоичных файлов, и хранит начальное нативное состояние, с которым собрана библиотека front профилей Free 6.11.1 и 7.3.1. `build` скачивает набор своего аппаратного адаптера в `.local/toolchains/qnx-guest/<digest>/` и при каждом использовании сверяет его с пинами, затем проверяет, что штатные библиотеки профиля экспортируют каждый импорт. Пока ресурсы не опубликованы и сервер отвечает HTTP 404, `build` запускает рецепт закреплённым Zig инструментов разработчика и сверяет результат с теми же пинами; без этого Zig он останавливается с `QNX_GUEST_ASSET_MISSING`.

`qnx-guest` запускается на Ubuntu 24.04 для тега `qnx-guest-<sha8>` или вручную. `src/dev/ci/qnx-guest-select.sh` выводит тег из пинов и проверяет URL и тег. Инструментами набора `linux` задание собирает тестовый исполняемый файл `qnx_guest_build_test`, чей режим `--recipe ROOT OUTPUT` запускает рецепт `build_qnx_guest_recipe` для четырёх аппаратных адаптеров компилятором clang и компоновщиком ld.lld закреплённого Zig. Двоичные файлы собираются дважды; обе копии должны побайтно совпасть друг с другом и с пинами. Запуск по тегу создаёт релиз с двоичными файлами и `SHA256SUMS` в ресурсах. Тест `qnx_guest_build` рабочего процесса `ci` на каждом хосте запускает рецепт набора `sa8155-qinggan09` и сравнивает его с пинами.

Изменение гостевого исходника меняет двоичные файлы: нужно запустить `qnx_guest_build_test --recipe "$PWD" "$PWD/.local/build/qnx-guest"`, внести SHA-256 файлов и URL нового тега в `qnxGuestModules` и отправить тег в `voyemu/voyemu-deps`.

## Рабочий процесс android-native

Нативные компоненты профилей — модель и симулятор CAN, помощник ранних входов, библиотеки среды выполнения и ввода, библиотеки нескольких дисплеев — собираются в CI из исходников компонентов и исходников AOSP, закреплённых в их `component.json`, закреплённым NDK и без оригиналов. Библиотека с `guestLibs` компонуется с заглушками, которые содержат только soname этих библиотек образа Android, поэтому её импорты остаются неразрешёнными до компоновщика Android; `build` проверяет, что библиотеки образа вместе с `libc.so`, `libm.so`, `libdl.so` и `libc++.so` экспортируют каждый импорт.

`androidNativeComponents` в `src/app/toolchain.json` закрепляет каждый компонент по ключу `<profile>/<component>`, `https://github.com/voyemu/voyemu-deps/releases/download/android-native-<sha8>/<profile>-<component>-<output>`, где `<sha8>` — начало SHA-256 файла `SHA256SUMS` со списком всех компонентов. `build` скачивает компоненты профиля в `.local/toolchains/android-native/<sha256>/` и при каждом использовании сверяет их с пинами. Заголовки и библиотеки Bionic поставляются только с NDK, поэтому без него рецепт не запускается: пока ресурс не опубликован и сервер отвечает HTTP 404, `build` запускает рецепт закреплённым NDK из `.local/toolchains/native-sdk/ndk/`, если его установил разработчик, и сверяет результат с тем же пином, а иначе останавливается с `ANDROID_NATIVE_ASSET_MISSING`.

`android-native` запускается на Ubuntu 24.04 для тега `android-native-<sha8>` или вручную. `src/dev/ci/android-native-select.sh` выводит тег из пинов и проверяет URL и тег. Действие `toolchains` устанавливает набор `linux` с входами `source-fixtures`, куда входит NDK; задание собирает тестовый исполняемый файл `native_component_test`, чей режим `--recipe ROOT OUTPUT --online` запускает `build_native_component_recipe` для каждого нативного компонента каждого профиля. Компоненты собираются дважды; обе копии должны побайтно совпасть друг с другом и с пинами. Запуск по тегу создаёт релиз с компонентами и `SHA256SUMS` в ресурсах.

Изменение нативного компонента меняет его ресурс: нужно запустить `native_component_test --recipe "$PWD" "$PWD/.local/build/android-native" --online`, внести SHA-256 файлов и URL нового тега в `androidNativeComponents` и отправить тег в `voyemu/voyemu-deps`.

## Рабочий процесс android-java

Собственный гостевой код Java профилей — исходники Java их компонентов и шагов патчей — тоже компилируется в CI: javac закреплённого JDK с `--release 8` и D8 закреплённых инструментов сборки против закреплённого `android.jar`, без оригиналов. Единица компиляции — каталог исходников с объявлениями `compile-only/`, необязательные исходники, которые aapt2 порождает из ресурсов компонента, и минимальный API; её ключ — SHA-256 относительного пути и SHA-256 каждого входного файла, минимального API и JAR платформы. `android-java.zip` содержит `<key>/classes*.dex` каждой единицы каждого профиля, `observer/classes.dex` — наблюдатель UI из `src/guest/android/api` без его тестов хоста — и `index.json`, который называет профиль и исходники каждого ключа и SHA-256 каждого исходника наблюдателя. `androidJava` в `src/app/toolchain.json` закрепляет его: `https://github.com/voyemu/voyemu-deps/releases/download/android-java-<sha8>/android-java.zip`, где `<sha8>` — начало SHA-256 файла `SHA256SUMS`. `build` скачивает его в `.local/toolchains/android-java/<sha256>/`, а помощник Java читает DEX каждой единицы по её ключу и останавливается с `ANDROID_JAVA_MISSING`, если в ресурсе нет единицы, как после правки гостевого исходника. С `--jdk` помощник может компилировать изменённые единицы из исходников; в среде Java по умолчанию нет javac, ей нужен закреплённый ресурс. Среда Java без javac тоже берёт наблюдатель из ресурса; `build` останавливается с `ANDROID_JAVA_MISSING`, если наблюдатель ресурса собран из других исходников. Исходники, которые используют классы оригинала, например компоненты с DEX-донором оригинала, синтетический телефон Free 6.11.1 и 7.3.1 и помощники USB-плеера и свойств MCU, компилируются против объявлений `compile-only/` ровно тех членов оригинала, которые они используют: имён, сигнатур и значений констант без кода.

`android-java` запускается на Ubuntu 24.04 для тега `android-java-<sha8>` или вручную. `src/dev/ci/android-java-select.sh` выводит тег из пина и проверяет URL и тег. Действие `toolchains` устанавливает набор `linux` с входами `source-fixtures`, куда входят библиотеки Maven, инструменты сборки и `android.jar`; задание компилирует исходники помощника и запускает `GuestJavaRecipe`, который раскладывает исходники компонентов каждого профиля так же, как `build`, с их закреплёнными внешними исходниками, связывает ресурсы APK-компонентов утилитой aapt2 и компилирует каждую единицу. Архив собирается дважды; обе копии должны побайтно совпасть друг с другом и с пином. Запуск по тегу создаёт релиз, ресурсами которого становятся `android-java.zip` и `SHA256SUMS`.

Правка гостевого исходника меняет архив: нужно скомпилировать исходники помощника, закреплённым JDK выполнить `java -cp CLASSES:LIBRARIES com.voyemu.prepare.GuestJavaRecipe "$PWD" "$PWD/.local/toolchains/java-sdk" "$PWD/.local/build/android-java"`, внести SHA-256 файла `android-java.zip` и URL нового тега в `androidJava` и отправить тег в `voyemu/voyemu-deps`.

## Рабочий процесс java-helper

Помощник Java подготовки тоже собирается в CI: `src/prepare/JavaHelperBuild.java` компилирует `src/prepare/java` утилитой javac закреплённого JDK против библиотек Maven, закреплённых в `src/prepare/libraries.json`, и JAR закреплённых инструментов сборки. `java-helper.zip` содержит `voyemu-java-helper.jar`, его `build-receipt.json` с контрольными суммами JAR и внешних зависимостей и библиотеки Maven в `lib/`; `d8.jar` и `apksigner.jar` в него не входят, подготовка берёт их из архива инструментов сборки. `javaHelper` в `src/app/toolchain.json` закрепляет его: `https://github.com/voyemu/voyemu-deps/releases/download/java-helper-<sha8>/java-helper.zip`, где `<sha8>` — начало SHA-256 файла `SHA256SUMS`.

Без `--jdk` подготовка устанавливает этот ресурс даже в рабочей копии исходников. Она добавляет два JAR из SDK и размещает помощник в `.local/toolchains/java-helper/<fingerprint>/`; этот ключ кеша связывает пин ресурса и пины внешних библиотек. Если ресурс отсутствует или недоступен, подготовка сообщает `JAVA_HELPER_ASSET_MISSING`, не компилируя замену. В рабочей копии исходников `--jdk PATH` выбирает рецепт разработчика; ключ его кеша учитывает также фактические исходники помощника и входные ресурсы. Оба варианта проверяют JAR, квитанцию сборки и полный набор внешних зависимостей, а также связывают выбранный ключ с квитанцией владения и каталогом кеша. Неполный кеш без квитанции владения сохраняется и отклоняется. Хеши исходников, используемые для кеша разработчика и проверок во время операции, не сохраняются как требования совместимости подготовленной машины.

`java-helper` запускается на Ubuntu 24.04 для тега `java-helper-<sha8>` или вручную. `src/dev/ci/java-helper-select.sh` выводит тег из пина и проверяет URL и тег. Действие `toolchains` устанавливает набор `linux` с входами `source-fixtures`; задание дважды собирает архив с упорядоченными записями и самым ранним временем ZIP; обе копии должны побайтно совпасть друг с другом и с пином. Запуск по тегу создаёт релиз, ресурсами которого становятся `java-helper.zip` и `SHA256SUMS`.

Правка исходника помощника или пина библиотеки меняет архив: нужно выполнить `javac --release 25 -d .local/build/java-helper/recipe src/prepare/java/com/voyemu/prepare/Json.java src/prepare/JavaHelperBuild.java`, затем закреплённым JDK `java -cp .local/build/java-helper/recipe com.voyemu.prepare.JavaHelperBuild asset "$PWD" "$PWD/.local/toolchains/java/libraries" "$PWD/.local/build/java-helper/asset"`, внести SHA-256 файла `java-helper.zip` и URL нового тега в `javaHelper` и отправить тег в `voyemu/voyemu-deps`.

## Рабочий процесс java-runtime

Среда Java подготовки — минимальный образ, который jlink собирает из jmods закреплённого релиза Temurin JDK 25, по одному на хост. `javaRuntime` в `src/app/toolchain.json` закрепляет версию JDK, список модулей, архив jmods каждого хоста по URL и SHA-256 и каждую среду в `javaRuntime.assets`: `https://github.com/voyemu/voyemu-deps/releases/download/java-runtime-<sha8>/java-runtime-<host>.zip` для `darwin-arm64`, `linux-x64` и `win32-x64`, где `<sha8>` — начало SHA-256 файла `SHA256SUMS` со списком трёх архивов. `deps` скачивает среду своего хоста в `.local/toolchains/java-runtime/<sha256>/`, и помощник на Java работает в ней, если `--jdk` не называет JDK. Пока ресурс не опубликован и сервер отвечает HTTP 404, `deps` собирает среды по рецепту ниже закреплённым JDK инструментов разработчика и сверяет архив своего хоста с тем же пином; без этого JDK `deps` сообщает с кодом `JAVA_RUNTIME_ASSET_MISSING`, что среда недоступна.

`java-runtime` запускается на Ubuntu 24.04 для тега `java-runtime-<sha8>` или вручную. `src/dev/ci/java-runtime-select.sh` выводит тег из пинов и проверяет URL и тег. С JDK из набора `linux` программа `src/prepare/JavaRuntimeBuild.java` скачивает три архива jmods, собирает каждую среду утилитой jlink этого JDK, версия которого должна совпадать с пином, и пишет ZIP с упорядоченными записями, самым ранним временем ZIP и режимами Unix. jlink собирает и jmods чужого хоста, поэтому все три среды собирает один исполнитель CI на Linux. В среде остаются только закреплённые модули, а отладочные атрибуты Java, заголовочные файлы и страницы руководства удаляются; нативные символы остаются, потому что для их удаления нужен objcopy хоста, а он не читает файлы Mach-O и PE. Рецепт отключает предварительную генерацию классов для MethodHandle: jlink может запускать этот плагин до или после удаления отладочных атрибутов Java, и от порядка зависят байты архива. Архив разделяемых данных классов (CDS) пришлось бы создавать средой каждого хоста, поэтому его нет. Каждый архив собирается дважды; обе копии должны побайтно совпасть друг с другом и с пинами. Запуск по тегу создаёт релиз, ресурсами которого становятся архивы и `SHA256SUMS`; тексты лицензий JDK лежат в `java-runtime/legal/`.

Правка рецепта, модулей или JDK может изменить архивы: нужно выполнить `javac -d .local/build/java-runtime/recipe src/prepare/java/com/voyemu/prepare/Json.java src/prepare/JavaRuntimeBuild.java`, затем закреплённым JDK `java -cp .local/build/java-runtime/recipe com.voyemu.prepare.JavaRuntimeBuild "$PWD" "$PWD/.local/toolchains/downloads/java-runtime" "$PWD/.local/build/java-runtime/asset"`, внести SHA-256 архивов и URL нового тега в `javaRuntime.assets` и отправить тег в `voyemu/voyemu-deps`. `java -cp .local/build/java-runtime/recipe com.voyemu.prepare.JavaRuntimeBuild modules "$PWD" HELPER_JAR` печатает модули, которые jdeps находит в собранном помощнике и его библиотеках, и завершается ошибкой, если какой-то из них не закреплён.

## Рабочий процесс uncrustify

Средство форматирования Uncrustify тоже собирается в CI, поэтому ни одному хосту не нужны для него Python и компилятор. `src/app/toolchain.json` закрепляет архив исходного релиза Uncrustify в `optionalTools.uncrustify` как вход рецепта, а исполняемый файл каждого хоста — в `optionalTools.uncrustify.binaries`: `https://github.com/voyemu/voyemu-deps/releases/download/uncrustify-<version>-<sha8>/uncrustify-<version>-<host>` для `linux-x64`, `darwin-arm64` и `win32-x64`, у последнего с `.exe`. `<sha8>` — начало SHA-256 файла `SHA256SUMS` со списком трёх исполняемых файлов, поэтому тег называет весь набор. `cmake -P src/dev/format/uncrustify.cmake` скачивает исполняемый файл хоста и сверяет его; см. [проверки](checks.ru.md#форматирование-и-checkstyle).

`uncrustify` запускается на Ubuntu 24.04 для тега `uncrustify-<version>-<sha8>` или вручную. Сначала `src/dev/ci/uncrustify-select.sh` выводит тег из пинов и проверяет, что каждый URL называет свой ресурс в этом релизе `voyemu/voyemu-deps`, а запуск по тегу использует именно этот тег. Задание устанавливает Zig, CMake, Ninja и архив через действие `toolchains` и собирает все три исполняемых файла через Zig на Linux: для Linux с `src/dev/toolchains/zig-linux-x64.cmake`, для Windows с `zig-windows-x64.cmake`, для macOS — с заголовками и библиотеками macOS из поставки Zig, поэтому файл не зависит от SDK хоста сборки. Таблицы опций сборка Uncrustify генерирует через Python 3 исполнителя CI. Каждый исполняемый файл собирается дважды, каждый раз в новом каталоге, который карта префиксов путей убирает из результата; обе копии должны побайтно совпасть друг с другом и с пином. Затем запуск по тегу создаёт релиз, ресурсами которого становятся три исполняемых файла и `SHA256SUMS`.

`cmake -DVOYEMU_UNCRUSTIFY_TARGET=<host> -DVOYEMU_UNCRUSTIFY_OUTPUT=<file> -P src/dev/format/uncrustify.cmake` — рецепт, который выполняет рабочий процесс, и способ воспроизвести исполняемый файл вне CI. Обновление Uncrustify: изменить пин архива, собрать этой командой три исполняемых файла, внести их SHA-256 и URL нового тега в `optionalTools.uncrustify.binaries` и отправить тег в `voyemu/voyemu-deps`. Набор `lint` устанавливает опубликованный исполняемый файл, а пока такого релиза нет, собирает его из исходников; оба пути сверяют один и тот же пин.

## Рабочий процесс release

`release` запускается при отправке стабильного тега в GitHub или вручную на теге предварительного релиза. Тег называет `VOYEMU_VERSION` из `src/app/CMakeLists.txt`, см. [релиз](release.ru.md#версия). Сначала он вызывает `ci`. Для предварительного релиза Windows выполняются нативные проверки Windows, проверки под Wine и проверки кросс-сборки Windows, тестовые наборы из исходников для Windows и Linux, тесты Linux и статический анализ. Для релиза на всех хостах три задания собирают лаунчер с `BUILD_TESTING=OFF` и наборами инструментов заданий `ci`: macOS arm64 на macOS 15 с графическим обработчиком, Linux x64 на Ubuntu 24.04 и Windows x64 кросс-сборкой на Ubuntu 24.04. Задания macOS и Linux проверяют, что лаунчер сообщает версию тега, macOS ещё проверяет подпись кода, а задание Windows — что PDB не появился; каждое задание устанавливает компонент `Runtime` и выгружает лаунчер и `notices/`. Задание `package` запускает `src/dev/release/archive.sh` для выбранных хостов, записывает `SHA256SUMS`, для стабильной версии заполняет формулу Homebrew через `src/dev/release/homebrew.sh` и берёт примечания к релизу из раздела версии в `CHANGELOG.md` через `src/dev/release/notes.sh`. Задание `windows-archive` на Windows сверяет SHA-256 архива с `SHA256SUMS`, распаковывает ZIP и проверяет версию лаунчера. Задание `release` создаёт релиз GitHub с архивами и `SHA256SUMS`, для версии с суффиксом — предварительный; только у него есть доступ на запись. Для стабильной версии задание `homebrew` отправляет формулу коммитом как `Formula/voyemu.rb` в `voyemu/homebrew-tap` с секретом `HOMEBREW_TAP_TOKEN` — токеном с правом записи в этот репозиторий; без секрета оно оставляет tap без изменений и сообщает об этом в запуске.
